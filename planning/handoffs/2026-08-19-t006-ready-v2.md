## CI works now, and it has a flake

The billing block cleared. Runs `32295504451` and `32296934644` are the first
CI executions this repo has ever had, and both really ran all four gates. A red
check is now genuine enforcement rather than an aspiration.

Two things to know before you trust it.

**It cannot print the test count.** The verdict block on CI says
`PASS test   counts unparsed`. Vitest emits ANSI styling without a TTY and
`summarize` in `scripts/gates.mjs` matches raw stdout. `PASS` is still correct
because it comes from the exit code, never from the parsed numbers, but the
evidence the runner exists to print is missing on the one surface built to be
trusted over a human summary. That is **T-027**.

**A 20-minute timeout against a 12m50s cold run.** A docs-only commit failed at
20m17s inside `npx playwright install --with-deps chromium`. A re-run passed in
under two minutes on warm caches. If you see a red `gates` check, read the log
before assuming your code broke: check whether the job was cancelled in the
install step. Also T-027.

## What T-023 changed, and what it did not

A write that changes `states.category` or reassigns `issues.state_id` is a
counter-affecting write and owes a repair, inside the same transaction.
Architecture §9 now says so. `PATCH /api/states/:id` repairs each affected
project; `DELETE` routes the reassignment through `runIssueWrite` per row, which
also buys `stateTimestamps` and the FM-016 blocker downgrade.

`tests/api/projects-choke-point.test.ts` now reports zero raw `issues` writes.
**Do not read that zero as "the §9 rule is enforced."** It inventories writes to
`issues` in `src/` only. `src/pages/api/teams/[id]/states/index.ts:104` already
runs `db.update(states)`, and adding `category` to that patch would reintroduce
the exact T-023 defect with the gate still printing zero. That is **T-026**.

## Two lessons from this round, both about evidence

**A falsification can pass vacuously even when the break lands.** CLAUDE.md
already covers the case where the edit silently matches nothing. This is the
other one: the edit lands and the assertion still could not have failed. Two
shapes hit it here. Asserting a cache is unchanged after an operation that
should not repair it cannot fail, because `repairProjectProgress` is idempotent
and rewrites the same numbers. Asserting `completedAt` is null after a write
that should clear it cannot fail, because `createIssue` never sets it and the
column was already null. The second was written after the first was caught,
which is the point: knowing about the trap does not prevent it. After writing an
assertion, ask what state would have to hold for it to fail. If nothing
reachable from the setup would, fix the setup.

**Hand reviewers a frozen commit, never a working tree.** Four reviewers ran
against a diff file while the tree kept changing under them. One spent six probe
rounds chasing a defect that had already been fixed and opened its report with
that complaint rather than a finding. Commit first, dispatch at
`git diff <base>..<sha>`, hold edits until every reviewer reports.

The review was still worth it. Three findings were real defects in the first
draft, not style notes: a guard comparing against a pre-`await` snapshot that
reintroduced the exact corruption the ticket existed to remove, a reassignment
that fixed counters but left `completedAt` and blocker relations behind, and
deliverable 3's transaction claim having no test that would notice it being
deleted.
